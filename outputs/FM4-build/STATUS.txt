STATUS FM4 RECOMPILATION - 16 Oktober 2026
========================================
Kode terakhir: 06ddcd6 (kurva tonemap B4). Default launcher baru (tanpa
workaround bayangan, anisotropic 16x, look pc) lolos gate smoke 16 Oktober
2026. Verifikasi build bersih: d1fa29a (13 Oktober 2026, verification.json)
dan runtime milik proyek (14 Oktober 2026, di bawah).

Tahap saat ini: build eksperimental yang menjalankan Quick Race, mode foto dan
balapan karier sampai hadiah pada binary terbaru (diuji otomatis lewat e2e).

terverifikasi.

yang berbeda. Keberhasilan historis tidak otomatis membuktikan bahwa fitur itu
sudah diuji ulang pada binary baru; yang diuji ulang tercatat di SKENARIO E2E

KETERBATASAN DAN MASALAH YANG MASIH ADA
-------------------------------------
- Kompatibilitas input saat ini dibatasi pada tiga XEX rilis Japan/Asia yang
  hash-nya dicatat dalam pipeline.py. Region/revisi lain, executable modifikasi
  dan title update ditolak. ISO harus diekstrak sendiri terlebih dahulu.
- Workflow hanya mendukung Windows x64 dengan toolchain dan GPU yang sesuai.
  Setup memeriksa prasyarat; tidak memasang Visual Studio, Python atau LLVM
  secara otomatis. Clone saja belum merupakan paket game siap jalan.
- Silau matahari terlalu terang (juga tembus ke kokpit) berasal dari query
  occlusion matahari yang melaporkan sekitar dua kali sampel yang diharapkan
  game. Launcher kini membagi dua hanya query yang ditunggu tersebut
  (--rov_occlusion_awaited_report_divisor=2); query seluruh frame untuk
  auto-exposure tidak diubah. Hasil uji visual 13 Oktober 2026: matahari tampil
  dan silau wajar pada kamera belakang dan kokpit. Faktor 2 ditentukan secara
  empiris, bukan dari perilaku perangkat keras Xenos yang sudah dibuktikan.
  Pembagi ini hanya berlaku di jalur ROV (-Rov); di jalur default RTV (query
  host) silau belum dikalibrasi.
- Noise warna, refleksi, tepi objek, seluruh kombinasi MSAA/skala resolusi dan
  kesesuaian dengan Xbox asli belum seluruhnya terverifikasi.
- Workaround bayangan tidak lagi bawaan launcher sejak 16 Oktober 2026 (lihat
  "Bayangan dan anisotropic filtering" di SKENARIO E2E GAMEPLAY). Shadow map
  dirender di semua kamera balapan tanpa bayangan kotak pada capture yang
  diperiksa; kesetaraan dengan Xbox asli belum dibandingkan.
- Shader sinkron menjadi bawaan untuk menghindari draw terlewat yang pernah
  menyebabkan foto hitam. Dengan cache kosong ia hanya menambah hitch saat
  memuat, tanpa menurunkan fps balapan (PENGUKURAN PERFORMA). Uji foto dengan
  cache shader kosong dan overwrite foto belum diulang pada build baru.
- Navigasi menu lewat input diagnostik: FM4 mengabaikan tekanan pertama setelah
  beberapa layar terbuka, dan menu karier serta GO RACE bersembunyi sekitar 9
  detik setelah tekanan terakhir (timer waktu nyata). Skenario e2e karenanya
  menekan sampai layar yang diharapkan terbaca lewat OCR, bukan menghitung
  tekanan; dengan cara ini navigasi menu andal.
- Pengemudi otomatis pengembangan sebelumnya dapat menabrak pembatas,
  kehilangan minimap dan gagal memulihkan arah; harness e2e sendiri hanya
  menahan gas. Pengujian kini memakai AI FM4 sendiri lewat opsi developer
  engageaionstart yang dibangun ulang (menang posisi 1 di Tsukuba). Ini alat
  pengujian, bukan fitur pemain.
- Masih ada fungsi layanan Xbox/runtime berupa stub. Tes instruksi sintetis
  tidak membuktikan seluruh kernel, audio, timing, sinkronisasi atau shader benar.
- Belum ada validasi lengkap semua mobil, lintasan, karier, Autovista, replay,
  audio, Kinect, multiplayer/online, DLC di luar Disc 2, dan sesi bermain panjang.
  Statusnya belum diverifikasi; tidak otomatis berarti semuanya rusak.
- Save/progres historis berhasil dimuat, tetapi kompatibilitas semua save dan
  migrasi profil antar-build/komputer belum dijamin. Workflow memakai profil

PENGUKURAN PERFORMA (13-15 OKTOBER 2026)
---------------------------------------
- Diukur dengan e2e/e2e.py --goal quickrace (Quick Race Bernese Alps, kamera
  kokpit, 30 detik terakhir balapan) pada komputer pengembangan: FPS median
  24-30, minimum sekitar 19-24.
- Thread command processor GPU menghabiskan sekitar 150-260 ms per detik
  menunggu resolve readback sinkron (--readback_resolve=full) dan 250-335 ms per
  detik menunggu occlusion query ROV, tetapi hampir tidak pernah menunggu
  perintah dari game. Hambatan utama saat ini adalah sinkronisasi GPU-CPU, bukan
  kode game hasil recompilation. Angka ini adalah baseline, bukan target.
- Baseline-v2 (counter baru, quickrace --repeat 3, fps_mean = frame dibagi
  waktu, 30 detik terakhir): 27,3 fps. Per frame: 1 report occlusion yang
  ditunggu game + 3 yang tidak, 0 viz query, 4 SET_BIN_SELECT dan sekitar 40%
  paket berpredikat dilewati (tiling terjadi). Run ulang binary yang sama:
  27,0 fps; median per run berbeda sampai 7%, jadi perbedaan < 10% tidak
  terbaca.
- A/B cvar baru pada binary yang sama (fps_mean, median 3 run):
    rov_occlusion_async=all                              30,0
    readback_resolve=fast                                31,0
    readback_resolve=none                                35,6
    rov_occlusion_async=all + readback_resolve=fast      55,8 (p99 52 -> 34 ms)
  Satu sinkronisasi saja yang dihapus hanya memindahkan tunggu ke sinkronisasi
  lainnya; keduanya harus hilang. Capture kokpit quickrace terlihat setara
  baseline. Atas keputusan pemilik proyek, kombinasi ini menjadi default
  launcher sebelum gate lengkap (digantikan RTV pada 14 Oktober 2026, lalu
  dikembalikan, dan sejak 15 Oktober 2026 RTV lagi; lihat di bawah).
- Timestamp GPU: dengan kombinasi di atas GPU sibuk sekitar 15,6 ms per frame
  (RTX 5070 Ti Laptop), resolve sekitar 0,2 ms. Thread command processor sibuk
  hampir penuh, jadi 60 fps stabil butuh pengurangan kerja GPU dan CPU (Tahap 2).
- Jalur RTV berjalan dan stabil 60 fps pada quickrace dengan
    --render_target_path_d3d12=rtv --edram_single_rt_no_wrap=true
    --rov_occlusion_async=previous
  (fps_mean 59,8-59,9, p99 sekitar 19,6 ms, GPU sekitar 10 ms per frame;
  ROV default: 54,3 fps, p99 35 ms, GPU 17,5 ms). Penyebab menu hitam: draw
  depth-only per tile mengikat satu render target, tingginya diperkirakan 720
  sehingga wilayah EDRAM-nya berputar melewati akhir EDRAM dan merebut tile
  warna di base 0; edram_single_rt_no_wrap mencegahnya. Report occlusion
  dihitung sebagai snapshot kumulatif dengan query host
  (rtv_occlusion_snapshots). Mode off/unawaited 35-49 fps; previous 60 fps.
- Masalah terbuka RTV (14 Oktober 2026): potongan jalan tertentu, terutama
  start straight (sekitar 4-14 detik setelah start), kadang tidak tergambar;
  yang tampak warna clear rata (102,102,102), sementara kerb dan objek lain
  tetap ada. Terjadi di sekitar 6 dari 28 run balapan RTV, dengan semua mode
  occlusion (all, previous, off), di kamera mana pun; tidak pernah terjadi di
  75 run ROV. Bukan karena timing atau nilai occlusion (query FM4 per frame
  berisi satu sprite matahari per tile; nilainya sama di ROV dan RTV), bukan
  uji depth EQUAL (FM4 tidak memakainya), dan bukan cache pipeline. Penyebab
  belum diketahui. e2e mendeteksinya lewat clear_gray_frames; jalur ROV
  (--render_target_path_d3d12=rov --rov_occlusion_async=all) tidak terkena.
  Klasifikasi (14 Oktober 2026, REX_DRAW_LIST_TRACE): di frame rusak game
  tetap mengirim semua draw yang ada di frame normal di sekitarnya, dan host
  menerbitkannya (outcome ok); garis dan panah di atas jalan tetap tergambar
  di atas warna clear. Jadi bukan culling game, melainkan warna draw yang
  hilang di jalur render target RTV. Kaitan dengan timing: dengan vblank_vrr
  (default sekarang) 0 dari 25 run RTV kena (13 ber-trace, 12 tanpa trace,
  53-60 fps); dengan vblank tetap 8 dari 36 (2/8 sekarang, 6/28 sebelumnya),
  p sekitar 0,01. Penyebabnya tersembunyi, bukan diperbaiki; RTV tetap opsi.
  Diagnosis ulang (15 Oktober 2026, RTV vblank tetap, sekitar 15% run kena):
  kesimpulan "warna hilang di jalur render target" di atas keliru. Frame graph
  tiap frame: di scene tidak ada transfer kepemilikan dan rentang klaim penuh
  (1024 tile). Statistik pipeline per draw (REX_DRAW_STATS) dan sensus paket
  draw di command processor (REX_BIN_TRACE): di area start game mengirim jauh
  lebih sedikit draw jalan (pasangan 630d5385/8c08d24c 16-25 paket per frame vs
  66-71 normal, 645fd4b2/89964d0 0 vs 36-46, ff6529eb/e3af5b04 5-7 vs 16-27);
  tidak ada yang dilewati predikasi bin, dan semua yang dikirim tergambar benar
  (vertex shader yang dijalankan di CPU dengan state guest yang sama memberi
  hasil clipping yang sama dengan GPU). Yang juga dikecualikan: tulisan CPU
  setelah data dipakai command processor, halaman shared memory basi pada
  rentang yang diminta, halaman valid yang tidak diawasi, halaman vertex yang
  ditulis GPU, readback resolve yang menimpa data guest, dan kecepatan (bug
  juga muncul pada 16 fps). Penyebab yang ditemukan sejauh ini ada di
  streaming track: trace baca file (REX_FILE_READ_TRACE) menunjukkan streamer
  di run normal membaca satu item Media\tracks\Alps\bin.zip dari offset
  0x4725000 sampai 0x4797000 (potongan 32 KB, dua buffer bergantian), di run
  rusak hanya 64 KB pertamanya lalu langsung pindah ke item berikutnya dan sisa
  item tidak pernah dibaca (juga baca 1 MB di 0x4725000 saat balapan tidak
  terjadi). Jadi game sendiri meninggalkan data track area start; renderer
  tidak terlibat. Penyebab akhir (15 Oktober 2026, trace I/O REX_IO_TRACE dan
  hook loader FM4_STREAM_TRACE): bukan I/O (baca streamer memakai event
  overlapped tanpa APC, semua selesai dan didekompresi tanpa error). Request
  item itu terdiri dari section .dat (0x110 byte) dan .gpu (1,5-1,8 MB, align
  4 KB); alokasi .gpu dari heap "sGPU" milik memory manager game gagal, loader
  menandai request gagal (flag +84 bit 4) dan membuangnya. Saat gagal sGPU
  (119,5 MB) terpakai 101,6 MB, puncak 119,3 MB: sekitar 18 MB bebas tetapi
  tidak ada blok 1,8 MB (alokator first-fit, terfragmentasi setelah lonjakan
  saat loading). Urutan muat di sini berubah-ubah karena penjadwalan thread
  host (beberapa worker loader, baca file seketika). Heap GPU lain di pool
  balapan punya cadangan: nGPU (41 MB, penuh) dan pGPU (front end) jatuh ke
  fGPU (118 MB, saat itu 33 MB bebas); sGPU tidak punya cadangan. Coba ulang
  alokasi selama 1 detik tidak membantu (memori tidak kembali bebas).
  Perbaikan (work/fm4-rex/src/fm4-streaming-fixes.cpp): bila alokasi section
  loader di sGPU gagal, sGPU diberi cadangan fGPU (field +236 = 0x22, seperti
  nGPU) lalu dialokasi ulang sekali; FM4_STREAMING_FALLBACK=0 mematikannya.
  Validasi RTV vblank tetap (kondisi bug paling sering), timeline tetap: 20 dari
  20 run tanpa frame jalan hilang, 5 run memakai cadangan dan semuanya berhasil
  (section 0x1C15A4 byte), 59,7-60,0 fps, tanpa crash; sebelumnya sekitar
  15-25% run kena.
